celld architecture walkthrough

One logical object, one current writer

Follow a Durable Object write from JavaScript to SQLite and shared storage, then see how celld prevents a failed or partitioned node from corrupting the object's next owner.

01

The five things to keep separate

IDENTITY

class:id names the logical object. It survives every process and activation.

RESIDENCY

A V8 realm is the object's temporary workspace. It is a cache, not durable storage.

STATE

A private SQLite database stores the object's durable application data and alarms.

AUTHORITY

A bucket record names the current owner and its monotonically increasing epoch.

RECOVERY

LTX ships SQLite WAL changes into an epoch-specific history in shared storage.

03

What the diagram is proving

Residency is not authority.

A node may still have the V8 realm and SQLite files, but it must stop serving after losing its lease or ownership epoch.

Local commit is not acknowledgement.

The response waits for LTX durability and a fresh ownership check. That is how celld targets RPO=0 for acknowledged writes.

An epoch is a data fence.

Every owner writes a separate LTX lineage. A seal fixes the recoverable end of an old epoch so late stale writes cannot reappear.
